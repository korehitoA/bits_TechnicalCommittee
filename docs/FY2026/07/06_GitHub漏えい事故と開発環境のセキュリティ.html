2026年6月 ／ 技術委員会
① なぜGitHubが狙われるのか ② 相次いだ事故 ③ 共通点 ④ 主な対策 まとめ
近年、多くの企業でGitHubを中心とした開発体制が採用されています。ソースコード管理だけでなく、CI/CDやクラウド環境との連携など、GitHubは開発基盤の中心的な存在となっています。

しかし2026年5月〜6月にかけて、GitHubを起点とした情報漏えいや不正アクセス事案が相次いで報告されました。これらの事例は、「本番環境を守る」という従来の考え方だけでは不十分であり、開発環境そのものが攻撃対象になっていることを示しています。
1

GitHubにはソースコードだけでなく、以下のような重要情報が保存されているケースがあります。攻撃者がこれらを取得すると、本番システムへ直接侵入できる場合があります。

2

相次いだGitHub関連事故

🔴 事例①

GitHub内部リポジトリ 約3,800件の情報窃取

2026年5月、GitHubは内部システムへの不正アクセスにより、約3,800件の内部リポジトリ情報が窃取されたことを公表しました。攻撃経路はコードエディタ「Visual Studio Code」の拡張機能を悪用した、従業員端末へのサプライチェーン攻撃とされています。

漏えいした情報にはソースコードや設定情報が含まれており、開発基盤自体が攻撃対象となるリスクを改めて示す事例となりました。GitHub側は影響範囲の調査とアクセス制御の強化を進めています。

🔴 事例②

CAMPFIREで認証情報流出による不正アクセス

クラウドファンディングサービスを運営するCAMPFIREでは、業務用途に使用していたGitHub認証情報が第三者に取得され不正アクセスが発生しました。攻撃者はその認証情報を公開サーバに意図的にアップロードするという手口で悪用し、最大22.5万件の個人情報が流出した可能性があると報告されています。

ソースコードそのものではなく、「認証情報の管理」が問題となった典型的な事例です。

🔴 事例③

マネーフォワードでGitHub経由の不正アクセス

マネーフォワードでは、GitHubアカウントへの不正アクセスによりリポジトリがコピーされる事案が発生しました。被害拡大を防ぐために銀行口座連携機能を一時停止し、認証情報の無効化・刷新や調査対応が実施されました。

開発環境への侵入が直接サービス停止につながることを示した事例です。なお、本番データベースへの侵害は確認されていないと公表されています。

事故から見える共通点

共通点① 認証情報が狙われている

攻撃者の目的はソースコードそのものではなく、クラウドやシステムへ接続するための認証情報であるケースが増えています。以下のような情報が漏えいすると、本番環境へ直接侵入される可能性があります。

AWS Access Key Azure認証情報 GitHub Personal Access Token APIキー DB接続情報

共通点② 開発環境と本番環境が密接につながっている

近年はCI/CDによる自動デプロイが一般的です。そのため開発環境への侵入が、本番環境への侵入につながるケースが増えています。

4

GitHubで実施できる主な対策

🔍 ① Secret Scanningの活用

GitHubにはSecret Scanningという機能があります。リポジトリ内にAPIキー・AWS認証情報・Azure認証情報・GitHub Tokenなどの機密情報が含まれていないかを自動検知します。誤ってコミットした場合でも早期発見が可能です。

設定はリポジトリの「Settings → Advanced Security → Secret Protection」から有効化できます。検知後は誰が・何を・どの順番で無効化するかまで手順を決めておくことが重要です。

APIキー検知 AWSキー検知 GitHub Token検知 早期発見

🔐 ② 多要素認証（MFA）の必須化

パスワードのみでは漏えい時に不正ログインを防ぐことができません。GitHubではMFA（多要素認証）・パスキー・ハードウェアセキュリティキーの利用を推奨しています。特に管理者権限を持つアカウントでは必須レベルの対策です。

MFA パスキー ハードウェアキー

🛡️ ③ 最小権限の原則

全員に管理者権限を付与するのではなく、開発者・レビュア・管理者など役割ごとに権限を分離します。万が一アカウントが侵害された場合でも被害範囲を限定できます。

ロールベース管理 最小権限 被害局限化

🚫 ④ シークレットをコードに埋め込まない

以下のような実装は避けるべきです。

API_KEY=xxxxxxxxxxxxxxxxxxxxxxxx PASSWORD=mysecretpassword123 DB_HOST=prod.internal.example.com

環境変数やSecrets Managerなどの仕組みを利用し、認証情報をソースコードから分離することが重要です。

API_KEY=${env.API_KEY} # 環境変数から取得 PASSWORD=${secrets.PASSWORD} # GitHub Secrets / AWS Secrets Manager DB_HOST=${env.DB_HOST}

📋 まとめ：SEとして押さえておきたい対策

  • GitHubを含む開発環境もセキュリティ対象として考える
  • 認証情報をリポジトリに保存しない（環境変数・Secrets Managerを使う）
  • Secret Scanningを有効化し、誤コミットを早期検知する
  • 管理者アカウントへのMFAを必須化する
  • 役割ごとの最小権限で運用する
  • CI/CDパイプラインの認証情報も定期的に棚卸し・ローテーションする

今後は「システムを守る」だけでなく、「開発環境を守る」ことがセキュリティ対策の重要なテーマになります。
