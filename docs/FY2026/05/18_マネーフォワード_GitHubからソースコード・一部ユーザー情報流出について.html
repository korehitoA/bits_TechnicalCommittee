マネーフォワードで発生した
GitHub不正アクセスと銀行口座連携停止

2026年5月に発生したマネーフォワードの障害・セキュリティインシデントについて、発生事例、原因、対応、過去の類似事例を技術者目線で整理します。内容は、マネーフォワード公式発表および各社の公式情報で確認できる範囲に限定しています。

発生事例経緯・原因対応状況類似事例

1発生事例の紹介

2026年5月、マネーフォワードグループが利用するソースコード管理サービス「GitHub」への不正アクセスが確認されました。これを受けて同社は、銀行口座連携機能を一時停止しました。

影響が公表されている主な機能は、『マネーフォワード ME』や『マネーフォワード クラウド』等で利用される銀行口座連携機能です。停止中は、対象金融機関の口座情報について、自動更新や手動更新ができない状態となりました。

対象機能
銀行口座連携
主な影響
銀行口座連携の停止
復旧状況
金融機関ごとに順次再開
ここが重要：今回の事例は、単なる画面エラーや一時的なサーバーダウンではありません。開発基盤への不正アクセスを起点に、金融機関連携の安全確認が必要になった事例です。

2発生した経緯・原因

公表内容によると、GitHubの認証情報が漏えいし、その認証情報を使って第三者がリポジトリへ不正アクセスしたとされています。さらに、リポジトリがコピーされたことも確認されています。

1. GitHub認証情報が漏えいGitHubへアクセスできる情報が外部に流出しました。
2. 第三者が不正アクセス漏えいした認証情報を使い、リポジトリへアクセスされました。
3. リポジトリがコピーソースコード保管領域がコピーされたことが確認されました。
4. 安全確認のため連携停止影響範囲を確認するため、銀行口座連携が一時停止されました。

本来置くべきではない情報が含まれていた点も問題

調査では、一部のリポジトリ内に、本来ソースコード管理上に含めるべきではない情報が存在していたことも説明されています。公式発表では、流出した可能性のある個人情報は、マネーフォワードケッサイ株式会社が提供する『マネーフォワード ビジネスカード』に関わる370件の「カード保持者名（アルファベット）」および「カード番号の下4桁」と説明されています。『マネーフォワード ME』や『マネーフォワード クラウド』の利用者全体がこの個人情報流出対象として公表されているわけではありません。

一方で、クレジットカード番号全桁・有効期限・セキュリティコード（CVV）は流出が確認されていないとされています。また、第二報では、本番データベースに格納された顧客情報や金融機関連携先のログインに必要な情報についても、漏えいや不正利用等の被害は確認されていないと説明されています。

3発生後の対応

マネーフォワードは、銀行口座連携機能を一時停止したうえで、不正アクセス経路の遮断、認証情報の刷新、ソースコードのセキュリティ検査、再発防止策の導入を実施したと公表しています。その後、システム全体の安全性確認が完了したことを受け、最終確認と接続準備が完了した金融機関から順次連携を再開しています。

  • 不正アクセスに関連する認証情報の無効化・再発行
  • 流出した可能性のある認証情報の無効化・再発行
  • ソースコードのセキュリティ検査と必要な追加対応
  • GitHub認証管理の厳格化、機密情報混入の自動検知、開発環境の監視強化
  • 金融機関ごとの最終確認後、銀行口座連携を順次再開
2026年5月14日時点の状態：全金融機関が一斉復旧したわけではなく、接続準備が整った金融機関から順次再開する形です。再開直後は更新集中により反映に時間がかかる可能性があります。また、停止期間中の資産推移は遡って自動記録されない旨も案内されています。

4過去の類似事例と対策

今回の事例は、「GitHubの認証情報」「リポジトリ内の情報」「外部連携サービスの停止判断」が関係しています。過去にも、ソースコード管理やCI/CD環境に保存された認証情報を起点に、情報漏えいや緊急対応が必要になった事例があります。

この章で見るポイント：過去事例を単に並べるのではなく、①何が起きたか、②どのように対応したか、③今回の事例にどう活かせるか、の順で確認します。
1
GitHub公開
トヨタ T-Connect関連：GitHub上のアクセスキー管理不備
ソースコード管理上に認証情報が含まれていた事例
何が起きたかGitHub上で公開されていたソースコードに、データサーバーへのアクセスキーが含まれていたことが判明しました。その結果、一部情報へアクセスできる可能性がある状態でした。
主な対応当該ソースコードの非公開化、アクセスキーの変更、アクセスログ調査などが実施されました。
今回との共通点：ソースコード管理上にあるべきではない情報や認証情報が含まれると、開発環境の問題にとどまらず、利用者情報のリスクにつながります。
2
CI/CD
CircleCI 2023年インシデント：シークレットのローテーション対応
CI/CD環境に保存された認証情報の見直しが求められた事例
何が起きたかCircleCIは、2023年1月のセキュリティインシデントを受け、顧客に対して環境変数やトークンなどのシークレットをローテーションするよう案内しました。
主な対応プロジェクト環境変数、コンテキスト変数、ユーザーAPIトークン、プロジェクトSSHキーなどのローテーションが案内されました。
今回との共通点：リポジトリだけでなく、CI/CDに保存されたシークレットも重要な管理対象です。漏えいの可能性がある場合、関係する認証情報を一括で無効化・再発行する運用が必要になります。

共通して言える対策

  • ソースコードや設定ファイルに認証情報を含めない
  • GitHubやCI/CD上のシークレットを定期的に棚卸しする
  • 漏えい時に、認証情報をすぐ無効化・再発行できる手順を用意する
  • GitHub Secret Scanningなどの検知機能を活用し、混入を早期発見する
補足：GitHub Secret Scanningは、リポジトリ内のAPIキー・パスワード・トークンなどを検出するための機能です。検知そのものだけでなく、検知後に誰が・何を・どの順番で無効化するかまで決めておくことが重要です。

5今回の事例から学べること

今回のポイントは、「ソースコードがコピーされた」ことだけではありません。公式発表上も、銀行法に基づく電子決済等代行業者としての責任や、提携金融機関との安全性確認を万全にするため、銀行口座連携機能を一時停止したと説明されています。

技術者目線のチェックポイント

  • 認証情報をソースコードや設定ファイルに直書きしない
  • GitHub、CI/CD、クラウドの権限を最小化する
  • 漏えい時に即時ローテーションできる手順を用意する
  • 金融機関など外部連携を伴う機能は、停止・再開の判断基準も含めて運用設計する
まとめ：便利なサービスほど、多くの外部システムとつながっています。今回の公表内容からは、復旧速度だけでなく、認証情報の刷新・安全性確認・金融機関ごとの最終確認を経て段階的に再開する対応が取られたことが分かります。
